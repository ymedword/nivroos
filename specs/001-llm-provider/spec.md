## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置一个 Agent 时声明模型供应商 (Priority: P1)

业务方定义 Agent 时，在配置中声明该 Agent 使用哪家供应商的哪个模型
（如 deepseek 的 deepseek-chat）。Agent 的任务指令只描述"做什么"，不包含
任何厂商相关的调用细节；发起对话后，Agent 用声明的供应商完成回答。

**Why this priority**: 这是能力一的唯一主链路——没有供应商接入，一切 Agent
能力无从谈起，且是本 user story 的最小可用切片。

**Independent Test**: 配置一个供应商（含模型与凭证）后，对 Agent 发起一次
对话，Agent 返回由该供应商模型生成的回答，即验证了整条链路。

**Acceptance Scenarios**:

1. **Given** 已配置供应商 A（名称、模型、凭证齐全），**When** 业务方配置的
   Agent 声明使用供应商 A 并收到一条用户消息，**Then** Agent 返回由供应商 A
   的模型生成的回答。
2. **Given** Agent 配置引用的供应商名称不存在，**When** 发起对话，
   **Then** 系统返回指明"供应商不存在"的清晰错误，不静默失败。
3. **Given** 供应商凭证对应的环境变量未设置，**When** 加载配置或发起调用，
   **Then** 系统报错并指明缺失的配置项。

---

### User Story 2 - 多供应商并存与无锁切换 (Priority: P2)

系统同时接入至少两家不同厂商的 LLM 服务（如 DeepSeek 与 Kimi）。不同 Agent
可分别使用不同供应商；同一个 Agent 换供应商只需改一处配置，任务指令零改动，
对话体验等价。

**Why this priority**: "运行时切换无 lock-in"是能力一的核心价值主张，也是
多 Agent 共用一个底座的前提。它建立在 P1 的单供应商链路之上，是自然的
第二步。

**Independent Test**: 配置两家供应商后，创建两个 Agent 分别声明使用其中
一家，两个 Agent 都能完成对话；随后把其中一个 Agent 的供应商改为另一家，
对话仍正常完成且 Agent 配置正文无改动。

**Acceptance Scenarios**:

1. **Given** 已配置两家不同厂商的供应商，**When** 两个 Agent 分别声明使用
   其中一家并各自收到消息，**Then** 两个 Agent 都返回各自供应商模型的回答，
   互不干扰。
2. **Given** 一个 Agent 当前使用供应商 A，**When** 只修改该 Agent 配置中的
   供应商名称为 B（任务指令不变），**Then** 后续对话由供应商 B 的模型生成。
3. **Given** 配置中出现两个同名供应商，**When** 加载配置，
   **Then** 配置校验拒绝并指出重复的供应商名称。

---

### User Story 3 - 每次调用可追溯（审计） (Priority: P3)

每次 LLM 调用自动留下一条审计记录：供应商名称、模型名、输入/输出/总 token
数、耗时、所属会话。运营与审计人员可以追溯"某次回复是哪个供应商哪个模型、
花了多少 token、耗时多久"。

**Why this priority**: 可审计是 NivroOS 的差异化定位（宪法原则五：审计表
Day One 写入），但它在价值上依赖前两条链路先跑通。

**Independent Test**: 发起一次对话（产生若干次 LLM 调用）后，逐条核对审计
记录：每次调用都有记录，且字段（供应商、模型、token、耗时、会话）与实际
调用一致。

**Acceptance Scenarios**:

1. **Given** 一次对话产生了 N 次 LLM 调用，**When** 对话结束后查询审计
   记录，**Then** 恰好有 N 条记录，每条包含供应商、模型、token 用量、耗时
   与所属会话。
2. **Given** 厂商响应中未返回 token 用量，**When** 写入审计记录，
   **Then** 对应字段记为空，不阻断对话、不报错。

---

### Edge Cases

- 供应商名称不存在或未配置任何供应商时发起对话 → 必须报错指明问题，不静默。
- 凭证未注入（环境变量缺失、为空）→ 加载配置时报错并指明缺失项。
- 供应商调用失败（网络错误、超时、厂商报错）→ 向调用方返回明确错误；
  核心阶段不自动切换、不静默重试。
- 多个供应商同名 → 配置校验拒绝。
- 厂商未返回 token 用量 → 审计字段记为空，不阻断。
- 厂商不支持结构化工具调用请求 → 该供应商对带工具调用的场景返回清晰错误。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持同时配置并接入至少两家不同厂商的 LLM 服务，
  且互不影响。
- **FR-002**: 每个供应商必须有唯一名称；配置至少包含访问凭证，可包含
  自定义服务地址。
- **FR-003**: 访问凭证必须经环境变量注入或独立本地配置文件加载；Agent
  配置文件中只允许 `${ENV_VAR}` 占位，不得出现明文凭证。
- **FR-004**: Agent 必须通过供应商名称引用供应商，并在 Agent 配置中指定
  模型；更换供应商不得要求修改 Agent 的任务指令。
- **FR-005**: 每次 LLM 调用必须写入一条审计记录，包含供应商名称、模型名、
  输入 token 数、输出 token 数、总 token 数、耗时、关联会话。
- **FR-006**: 供应商调用失败必须向调用方返回明确错误；核心阶段不做自动
  切换与静默重试。
- **FR-007**: 配置加载必须校验必填项与格式；缺失或非法时必须给出指明
  具体配置项的清晰报错，不静默失败。
- **FR-008**: 系统必须支持带结构化工具调用请求的对话调用：模型的工具调用
  请求原样返回给调用方，是否执行由上层循环决定（本能力不代执行）。
- **FR-009**: 同名供应商配置必须被校验拒绝并指出重复名称。
- **FR-010**: 未配置任何供应商或引用的供应商不存在时，系统必须报清晰错误。

### Key Entities

- **Provider（供应商）**：LLM 服务的接入配置。属性：唯一名称、访问凭证
  （环境变量注入或独立本地配置文件）、可选自定义服务地址。模型由 Agent
  配置按需指定；Provider 被 Agent 配置按名称引用。
- **LLM Call 记录（审计）**：每次 LLM 调用的可追溯记录。属性：关联会话、
  供应商名称、模型名、输入/输出/总 token 数、耗时、发生时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 核心阶段验收时，DeepSeek 与 Kimi 两家厂商的模型跑通完整
  对话（需求文档 §13 验收口径，两家凭证均已就位）。
- **SC-002**: 更换供应商只需修改一处配置，Agent 任务指令零改动。
- **SC-003**: 100% 的 LLM 调用产生审计记录，且供应商、模型、token 用量、
  耗时四类字段与实际调用一致（厂商未返回 token 的按空记录）。
- **SC-004**: 配置缺失或非法时，100% 的场景给出指明具体配置项的清晰报错。
- **SC-005**: 与能力二合跑的验收 Demo 一（`nivroos chat` 查天气穿衣）
  完整通过——本 user story 没有独立可见入口，Demo 一是其联合验收锚点。

## Assumptions

- 核心阶段跑通 DeepSeek 与 Kimi 两家（需求文档 §13 验收口径，两家凭证均已
  就位）；Kimi 无官方 GA starter，经 OpenAI 兼容通道接入（见 plan
  research §1）。其余厂商不在本 user story 内逐家验证。
- 接入基线为 OpenAI 兼容协议；不支持该协议的厂商不在核心阶段范围内。
- 核心阶段不做 fallback、hedge racing、动态路由与成本看板（放扩展阶段）；
  供应商故障直接报错。
- 核心阶段部署假设内网，无认证机制。
- token 用量依赖厂商在响应中返回；未返回时按空记录处理。
- 依赖：能力二（US-2 ReAct 循环）用于消费工具调用请求并完成联合验收
  Demo 一；本 user story 单独验收覆盖 P1/P2/P3 三条链路。
