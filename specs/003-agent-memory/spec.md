# Feature Specification: US-3 Memory 三层记忆（让 Agent 跨对话记得住）

**Feature Branch**: `003-agent-memory`

**Created**: 2026-09-30

**Status**: Draft

**Input**: 模块执行颗粒度文档 `docs/us/us3-memory.md` 第 1、2 节（module-dev 步骤 2 骨架组装）：
Memory 三层记忆——Agent 跨对话保留状态的统一门面，核心阶段做会话与长期两层。

## Clarifications

### Session 2026-09-30

- Q: 长期记忆读写失败时，系统应该怎么办？（颗粒度文档 §2.2-8 只说「记 WARN
  日志」与「catch 不吞」，没说失败后是继续还是中断；且 `save` 走工具审计路径、
  `load` 在上下文组装里不是工具调用，没有审计路径） → A: 区分读写。写入失败
  上抛，走既有工具失败审计（`success=false`），让模型知道没记住；读取失败记
  WARN 日志后按「本轮无长期记忆」继续，保证对话主链路不被外部记忆服务抖动
  拖垮。写入是 Agent 的显式承诺必须让它知道成败，读取是每轮必经路径故可用性
  优先；「不吞」体现为日志与审计双轨，而非静默。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 主动记住偏好并在后续会话复现 (Priority: P1)

用户在对话中透露自己的项目信息，Agent 判断值得长期保留并主动写入记忆的
核心区；用户重启系统或新开会话后提出相关问题，Agent 的答复体现此前记下的
偏好，用户不需要重新解释背景。

**Why this priority**: 这是本模块的主链路与 Demo 二的验收场景——"记住 →
跨会话复现"完整闭环，也是 Agent OS 区别于 chatbot 的核心体验；其他场景都是
它的变体或支撑条件。

**Independent Test**: 以真实模型跑两轮对话——第一轮告知"我的项目用
Spring Boot，部署在 K8s 上"，核对长期记忆载体中出现该条且审计记录成功；
重启进程后第二轮问"帮我看看我的项目能用什么数据库"，Agent 回复引用
Spring Boot/K8s 语境（Demo 二人工验收）。

**Acceptance Scenarios**:

1. **Given** 用户在新会话中透露值得长期保留的信息，**When** 模型请求调用
   `save_memory` 且指定写入核心区，**Then** 系统把该条追加到长期记忆的
   核心区，并在审计记录中留下成功条目。
2. **Given** 核心区已记下用户偏好，**When** 用户在新会话（或重启进程后）
   提出相关问题，**Then** 该偏好出现在本轮组装的上下文里，Agent 的答复
   体现它，无需用户重复说明。
3. **Given** 模型调用 `save_memory` 时未指定分区，**When** 系统处理该次
   写入，**Then** 内容进入归档区而非核心区。
4. **Given** 模型在上一轮写入了一条记忆，**When** 下一轮组装上下文，
   **Then** 新内容已被读到（不缓存，写入立即可见，无需重启进程）。

---

### User Story 2 - Agent 按关键词检索历史归档记忆 (Priority: P2)

用户问起过去讨论过的内容，Agent 对归档区做关键词检索，命中后复述给用户；
核心区因为每轮全量注入，不参与检索。

**Why this priority**: 归档区是长期记忆中体量增长的部分，无法全量注入，
必须可检索；但它的价值建立在 P1 的写入与注入链路之上。

**Independent Test**: 预先向归档区写入若干条含特定关键词的记忆，让 Agent
处理一个含该关键词的问题，核对其检索命中并把内容带回回复；同时核对核心区
内容不作为检索结果来源。

**Acceptance Scenarios**:

1. **Given** 归档区存在含某关键词的记忆，**When** 模型请求调用
   `recall_memory` 并给出该关键词，**Then** 系统在归档区做关键词匹配并
   返回命中内容。
2. **Given** 某关键词只出现在核心区、不在归档区，**When** 模型请求调用
   `recall_memory`，**Then** 检索结果不包含核心区内容（核心区不参与检索）。
3. **Given** 归档区没有任何记忆匹配该关键词，**When** 模型请求调用
   `recall_memory`，**Then** 系统明确返回"无匹配"，不返回编造内容。

---

### User Story 3 - 运维方切换长期记忆的存储形态 (Priority: P3)

部署方通过修改一行配置切换长期记忆的存储形态（文件 / 数据库 / 外部自托管
记忆服务），门面及以上（上下文组装、两个记忆工具、ReAct 循环）不需要改动，
已有的"核心区 / 归档区"语义在新形态下保持一致。

**Why this priority**: 这是接口墙价值的兑现——记忆量增长或需要语义检索时
能低成本升级；但核心阶段多数部署用默认形态即可，故优先级最低。

**Independent Test**: 以默认形态跑通 P1 场景后，改配置切到数据库形态并重启，
重复同一组场景，核对行为一致且上游代码零改动。

**Acceptance Scenarios**:

1. **Given** 系统以默认文件形态运行并已写入记忆，**When** 部署方把存储形态
   配置改为数据库并重启，**Then** 系统正常启动，同一套记忆读写场景仍然通过。
2. **Given** 部署方把存储形态改为外部自托管记忆服务，**When** 该服务凭据
   未配置或写成明文，**Then** 系统拒绝启动并给出清晰报错，不静默降级。
3. **Given** 任一存储形态下，**When** 部署方查看配置，**Then** 归档区截断
   阈值是可配置项（默认 4000 字符）。

---

### Edge Cases

- **归档区超出配置阈值**：只截断归档区；核心区内容完整保留，不受阈值影响。
- **核心区自身膨胀**：契约规定核心区永不截断，因此核心区过大会推高每轮
  上下文长度；这是已知代价，由 Agent 自行克制写入，系统不代它做取舍。
- **长期记忆载体首次不存在**：视为空记忆，系统正常启动与工作，不报错。
- **长期记忆载体存在但内容为空**：同上，视为空记忆。
- **写入失败（文件不可写、数据库异常、外部服务不可达）**：失败进入既有工具
  失败审计路径，模型得知未记住；不静默当作成功，不产生"假承诺"。
- **读取失败（载体损坏、数据库异常、外部服务不可达）**：记 WARN 日志，本轮
  按无长期记忆继续，对话不中断；下一轮重新尝试读取，失败结果不被缓存。
- **并发写入**：多会话同时写记忆时不得丢写或损坏载体。
- **检索词由模型给出而非用户原话**：模型自行从用户问题中提取关键词，
  系统不做同义词扩展或语义改写。
- **记忆正文格式**：不做严格约束，模型用自然语言写入即可，系统不校验内容结构。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在每轮组装上下文时重新读取长期记忆，不做缓存——
  写入后下一轮立即生效，无需重启进程。
- **FR-002**: 长期记忆 MUST 划分为「核心区」与「归档区」两个分区，该语义
  在所有存储形态下保持一致。
- **FR-003**: 系统 MUST 保证核心区内容永远完整注入、绝不被截断。
- **FR-004**: 系统 MUST 只对归档区做截断；截断阈值 MUST 可配置，默认
  4000 字符。
- **FR-005**: 写入核心区还是归档区 MUST 由 Agent 通过写入参数显式指定，
  系统不猜测、不做自动分类。
- **FR-006**: 写入未指定分区时，系统 MUST 默认写入归档区。
- **FR-007**: 系统 MUST NOT 在核心阶段做记忆自动抽取（不从对话历史自动
  提炼记忆），分区完全由 Agent 的调用时机与参数决定。
- **FR-008**: 系统 MUST 提供关键词检索能力，不做语义检索或向量检索。
- **FR-009**: 检索 MUST 只作用于归档区；核心区不参与检索。
- **FR-010**: 长期记忆 MUST 通过两个内置工具暴露给 Agent：`save_memory`
  （写入，接受内容与分区参数）与 `recall_memory`（按关键词检索）。
- **FR-011**: 记忆写入 MUST 走系统既有的工具审计机制，成功与失败都落库。
- **FR-012**: 写入长期记忆（`save_memory`）失败时，系统 MUST 让失败进入既有
  工具失败审计路径（记录失败条目与错误信息），使模型得知写入未成功，MUST NOT
  让模型误以为已记住。
- **FR-021**: 读取长期记忆失败时，系统 MUST 记 WARN 日志，并按「本轮无长期
  记忆」继续该轮对话；MUST NOT 因读取失败而中断整轮对话。
- **FR-013**: 长期记忆的存储形态 MUST 可插拔，支持三种形态：文件（默认）、
  数据库、外部自托管记忆服务。
- **FR-014**: 切换存储形态 MUST 只需修改配置项 `memory.backend`，上下文
  组装、两个记忆工具与 ReAct 循环 MUST NOT 需要改动。
- **FR-015**: 长期记忆载体的路径/地址 MUST 由系统固定，MUST NOT 走通用
  文件工具的路径白名单校验（它不是用户可指定的任意路径）。
- **FR-016**: 外部记忆服务的凭据 MUST 只允许环境变量占位（双通道：环境
  变量或本地密钥文件）；明文写入配置 MUST 被拒绝。
- **FR-017**: 凭据缺失或非法时，系统 MUST 给出清晰报错，MUST NOT 静默失败
  或降级。
- **FR-018**: 长期记忆内容 MUST 每轮注入到送给模型的上下文里。
- **FR-019**: 系统 MUST 把会话历史与长期记忆收口在同一个记忆入口之后，
  使 ReAct 循环无需分别向两个来源索取上下文。
- **FR-020**: 首轮运行且长期记忆载体不存在时，系统 MUST 视为空记忆正常
  启动，MUST NOT 报错。

### Key Entities

- **记忆条目（Memory Entry）**：一条长期记忆，含内容、所属分区、写入时间。
  是长期记忆的最小单位。
- **记忆分区（Scope）**：取值「核心区」或「归档区」，含义固定——核心区
  每轮全量注入且永不截断；归档区可截断、可检索。分区是跨存储形态稳定的
  语义，不随存储形式变化。
- **长期记忆存储（Long-Term Memory Store）**：承载分区语义的可插拔持久化
  载体，对外提供追加、全量读取、关键词检索三个能力。
- **记忆入口（Memory Service）**：对上层唯一的记忆读写门面，向下收口会话
  历史与长期记忆两个来源。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Demo 二完整通过——用户在新会话中不重复解释背景的前提下，
  Agent 的答复体现此前记下的偏好（P1 场景全部通过）。
- **SC-002**: 归档区被塞入远超阈值的内容后，核心区内容保留率 100%。
- **SC-003**: 记忆写入后生效延迟为 0 轮——下一次组装上下文即可见，过程中
  不需要重启进程。
- **SC-004**: 切换存储形态后，同一套验收场景 100% 通过，且上下文组装、
  记忆工具、ReAct 循环三处零改动。
- **SC-005**: 记忆写入无论成功或失败，100% 可在审计记录中追溯。
- **SC-006**: 核心区内容在归档区被截断的同一轮上下文中完整出现，不出现
  "核心区被连带截断"的任何一次。

## Assumptions

- **会话记忆复用既有能力**：会话历史的存储与管理由 US-2 已交付的会话管理
  承担，本模块不重建；本模块的职责是把它与长期记忆收口到同一个入口之后。
- **会话存储保持内存版**：会话持久化到数据库归 US-5，不在本模块范围。
- **外部记忆服务未就绪**：自托管外部记忆服务在本阶段不可用，本模块只交付
  集成代码与单元测试覆盖；真实联调列为人工验收项，待服务就绪后执行。
- **记忆体量为小规模**：核心阶段单部署的记忆条数在数十到数百量级，因此
  纯关键词匹配与字符串截断足够，无需索引或向量能力。
- **模型自行克制写入**：Agent 是否值得记、写哪个分区由模型判断；系统提供
  能力但不干预，核心区膨胀的风险由 Prompt 指令与使用反馈调节。
- **单条消息长度沿用既有约束**：既有系统对单条消息有长度上限，记忆写入
  的内容长度受其约束，本模块不另设限制。
- **分区语义跨形态稳定**：换存储形态时「核心区 / 归档区」的语义不变，
  变化只发生在存储形式上。
- **截断保留最近的内容**：颗粒度文档 §2.3 的伪代码只写 `truncate(maxChars)`
  未给方向。按记忆系统的通行取舍，截断**丢弃最旧的归档条目、保留最新的**——
  时间上越近的记忆越可能相关；若反向截断会静默丢掉最有价值的近期记忆。
- **长期记忆载体是部署级共享的**：技术方案 §5.2 把载体路径固定为
  `.nivroos/memory/MEMORY.md`（单一路径，无 per-agent 子目录），因此同一部署
  内的多个 Agent 共用同一份长期记忆。这是技术方案定死的字面量，本模块不改；
  但 plan 与测试 MUST NOT 假设 Agent 之间存在记忆隔离。

## Dependencies

- **依赖 US-1 交付**：模型供应商抽象与调用审计能力（记忆写入的审计走既有
  工具审计机制，模型调用本身走既有调用审计）。
- **依赖 US-2 交付**：ReAct 循环、会话管理、上下文组装器、内置工具池。
  本模块需要扩展上下文组装器（接入记忆入口）与工具池（加入两个记忆工具），
  这两处改造已在颗粒度文档 §3.2 列为前序改造点，实施时停下报告。
- **外部依赖**：自托管记忆服务（外部形态用），核心阶段仅交付集成代码与
  单元测试。

## Out of Scope

- 自动抽取（对话结束自动提炼记忆）
- 内置向量库 / 语义检索（关键词匹配即可）
- 情景记忆（三层中的第三层）
- Memory Wiki（结构化 claim/evidence、矛盾检测）
- 记忆压缩（超长只做简单截断，总结压缩放扩展阶段）
- 知识图谱后端
- 记忆入口层的缓存（扩展阶段再加缓存与失效机制）
- 会话落库（会话存储保持内存版，US-5 换数据库）
