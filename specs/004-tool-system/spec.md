## Clarifications

### Session 2026-09-30

- Q: 技能（Skill）元数据注入的「本地绝对路径」指哪条路径——Agent 本地 `skills/`
  下的软连接路径，还是软连接解析后的真实目标路径？两种取法会撞上文件白名单：
  §3.3 示例配置的白名单只有 `.nivroos/agents`，若注入真实目标路径
  （`.nivroos/skills/<name>/SKILL.md`），模型按 L1 提示去 `read_file` 会被
  白名单拒绝，渐进披露的 L2 整条断掉。 → A: 注入 **Agent 本地绝对路径**
  （即软连接路径，形如 `.nivroos/agents/<agent>/skills/<name>/SKILL.md`）。
  依据技术方案 §8.3 原文「只注入 Skill frontmatter 的 name/description 与
  **Agent 本地绝对读取路径**」与 §11.1「L1 每轮注入当前 Agent 已绑定 Skill 的
  name、description 和本地绝对路径」；该路径位于 `.nivroos/agents` 之下，
  与 §3.3 示例白名单自洽，零额外配置即可工作；软连接由运维方放置，
  本身就是一次授权动作。

- Q: 技能绑定的安全边界是什么？软连接可以指向任意位置吗？ → A: 不可以。
  技术方案 §8.3 要求「验证**真实目标位于公共 Skill 根**」——每轮扫 `skills/`
  时解析软连接真实目标，必须落在公共技能库（`.nivroos/skills/`）之内，
  否则告警跳过该技能、不注入、不阻断对话。此项为技术方案明写、而颗粒度
  文档 §3.1/§3.2 未列出的校验，按「文档与最新技术方案冲突以技术方案为准」
  落地（软门禁报告项，见收尾报告）。

- Q: 命令工具在哪个工作目录下执行？ → A: 进程启动目录（工作区根，即
  `.nivroos/` 的父目录）；命令经 POSIX `bash -c` 执行（颗粒度文档「待决事项」
  默认建议）。技术方案未规定，取"模型可自行在命令里写相对或绝对路径"的
  最简默认，不额外引入工作目录配置键。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 在白名单内读写文件、执行命令、调用接口 (Priority: P1)

模型接到"看一下这个目录里有什么、把内容读出来、跑个脚本处理一下"这类任务时，
连续调用文件工具与命令工具完成任务；每一步动作在真正发生之前先过白名单校验，
白名单之外的动作被拒绝且**没有真正发生**——模型收到明确的失败原因后换一条
可行的路径继续。

**Why this priority**: 这是本模块的主链路，也是"Agent 能干事"的最短闭环
（需求文档 §5.6；技术方案 §6.2 九个内置工具中的八个）。工具同时是安全边界：
白名单校验与工具执行是同一条链路，先交付它才能让后续三档接入共用同一套安全
底座。

**Independent Test**: 单测层以临时目录与无副作用命令跑通读写/列目录/执行/
HTTP 四类工具的放行与拒绝两组用例（含 `../` 穿越、白名单外域名），并断言被拒
动作**未发生**（目标文件不存在、请求未发出）；真机层用 `nivroos chat` 让模型
跑一次"列目录 → 读文件 → 执行脚本"。

**Acceptance Scenarios**:

1. **Given** 路径白名单包含工作区内某目录，**When** 模型调用文件工具读写该
   目录下的文件，**Then** 动作完成，结果进入对话上下文。
2. **Given** 模型给出的路径经规范化后越出白名单（含 `../` 穿越），**When**
   模型调用文件工具，**Then** 动作被拒绝、给出失败原因，且目标文件**没有被
   创建或修改**。
3. **Given** 命令白名单包含某程序，**When** 模型调用命令工具执行该程序，
   **Then** 命令执行、标准输出进入结果；**When** 模型执行白名单外的程序，
   **Then** 动作被拒绝且命令**没有被启动**。
4. **Given** 命令执行时间超过配置的超时，**When** 模型调用命令工具，**Then**
   命令被终止并返回失败，进程不挂死。
5. **Given** 任一档白名单配置为空，**When** 模型调用对应工具，**Then** 一律
   拒绝（空配置是"全部拒绝"，不是"不校验"）。

### User Story 2 - Agent 主动把结果推送到企业群 (Priority: P2)

到点自动跑完的日报类任务没有人在另一端等着响应，Agent 必须主动把结果送出去。
运维方在全局注册表里登记一个通知渠道（名称 + 类型 + 地址 + 说明），Agent 在
任务指令里按名引用；模型调用通知工具时只需给出内容与渠道名，真实地址不进入
对话。

**Why this priority**: 这是"入站有人推、出站能主动送"的对称能力，是日报/告警
类 Agent 的出口；但它建立在 P1 的沙箱底座之上（发送前要过同一份域名白名单），
故排在 P1 之后。

**Independent Test**: mock 发送通道，断言渠道名解析出的目标地址与类型正确、
发送前必须先过域名白名单（顺序断言）、白名单外地址请求未发出、渠道名缺失或
不存在时明确失败并回填可用渠道名；真机层用一个真实群机器人 webhook 收一次
推送、并验证未登记域名被拒。

**Acceptance Scenarios**:

1. **Given** 注册表里存在名为 `ops-team` 的渠道，**When** 模型调用通知工具
   并给出该渠道名与内容，**Then** 内容被推送到该渠道登记的地址，审计记录成功。
2. **Given** 渠道登记地址的域名不在 HTTP 白名单内，**When** 模型调用通知工具，
   **Then** 动作被拒绝、请求**没有发出**，且失败原因可追溯。
3. **Given** 模型未提供渠道名，**When** 调用通知工具，**Then** 系统明确失败
   并在错误信息中给出可用渠道名清单（不猜、不静默）。
4. **Given** 模型提供了一个不存在的渠道名，**When** 调用通知工具，**Then**
   失败并回填可用渠道名清单。
5. **Given** 通知发送链路被调用，**When** 检查执行顺序，**Then** 白名单校验
   发生在发送之前（顺序反了即是绕过漏洞）。

### User Story 3 - 工具统一注册与三类来源统一取用 (Priority: P3)

同一套"工具"概念容纳三类来源：NivroOS 自带的内置工具、业务方用注解标注的
Java 组件、外部进程经协议暴露的工具。三类工具在运行时被同等对待、按名取用；
模型侧只看到工具名、描述与入参 schema，不感知来源。每个 Agent 只拿到自己在
目录里声明的那些工具——工具池就是能力边界。

**Why this priority**: 三档接入方式共用的注册与取用基础设施（技术方案 §6.5、
§6.6）；它是方式一/方式二/方式三回报用户的前提，但自身不直接产生业务能力，
故列 P3。

**Independent Test**: 注册表内注册三类来源各一个工具，参数化断言三类工具的
名称非空且唯一、描述非空、入参 schema 非空；核对按名查找命中与未命中行为；
核对某 Agent 声明两个工具时工具池**恰好**只有这两个。

**Acceptance Scenarios**:

1. **Given** 一个被注解标注的组件，**When** 启动扫描完成，**Then** 它的每个
   标注方法都成为一个可调用工具，名称/描述/入参 schema 来自注解，且与内置
   工具走同一条扫描注册路径。
2. **Given** 任意一个已注册工具，**When** 取出它的入参 schema，**Then**
   schema 非空（任一工具 schema 为空会让**全部**模型调用失败）。
3. **Given** Agent 目录声明了两个工具名，**When** 该 Agent 的一轮对话组装
   可用工具，**Then** 工具池恰好是这两个——未声明的内置工具不进入。
4. **Given** 模型请求调用一个未注册或未声明的工具名，**When** 处理该调用，
   **Then** 记告警并跳过，不中断本轮对话。
5. **Given** 同一工具名被重复注册，**When** 完成注册，**Then** 先注册者保留、
   后注册者不覆盖并记告警（内置工具不被外部工具静默顶掉）。

### User Story 4 - 轻代码接入：业务方自写 MCP server (Priority: P4)

业务方用任意语言写一个 MCP server，在配置里声明名称、传输方式、启动命令与
环境变量，NivroOS 启动时把它连上、拉取工具列表并注册。单个 server 连不上
只告警跳过，不阻断启动；调用失败时错误文本回到模型手里，模型自己决定换路。

**Why this priority**: 这是零代码方式一（复用社区现成 MCP server）与方式二的
共同技术底座，也是"每日科技日报"验收 Demo 的能力组成部分；但它对用户的价值
以 P3 的注册表为前提，故列 P4。

**Independent Test**: 以 mock 传输层注入一个失败 server 与一个正常 server，
断言启动不抛异常、正常 server 的工具被注册、失败 server 的工具未注册、告警
日志产生；单测层以 mock 客户端断言工具调用参数转发与错误结果映射。

**Acceptance Scenarios**:

1. **Given** 配置里声明了两个 MCP server 且其中一个启动命令不存在，**When**
   系统启动，**Then** 启动完成不中断，可用的那个 server 的工具全部注册，
   失败的 server 被跳过并留下告警。
2. **Given** 某个 MCP 工具被模型调用，**When** 转发给 server 执行，**Then**
   入参按协议原样转发，返回的文本内容成为工具结果。
3. **Given** MCP server 返回错误结果（`isError`），**When** 该结果回到系统，
   **Then** 工具结果标记为失败，且错误文本被回填进对话上下文（模型看不到
   原因就不会收敛）。
4. **Given** 配置里某个环境变量的值是明文而非占位符，**When** 解析该配置，
   **Then** 系统大声报错拒绝，不静默放行；占位符指向的环境变量缺失时同样报错。

### User Story 5 - 零代码上线：Agent 目录完整派生与技能按需披露 (Priority: P5)

业务方不写 Java 代码，只写一个 Agent 目录：运行配置放在文件头（描述、身份、
可用工具、引用的 MCP server、引导文件、渠道、定时任务），任务指令放在正文。
启动时系统扫描所有 Agent 目录并注册；绑定的公共技能只注入名称、描述与本地
路径，正文由模型需要时用文件工具现取——不预载、不占上下文。

**Why this priority**: 这是"一个目录 = 一个 Agent"（宪法原则四）的兑现，也是
方式一零代码上线的最后一环；它依赖 P1（文件工具）与 P3/P4（工具注册）才能
被真正验证，故列最后。

**Independent Test**: 以多 Agent 目录（其一配置非法）启动扫描，断言合法者全部
注册、非法者只告警；断言 Agent 声明的引导文件列表生效、缺失时回退默认三件并
告警；挂一个真实技能软连接，断言注入文本含名称/描述/绝对路径且**不含技能
正文**，并核对每轮重扫（新增技能下一轮可见、移除即消失）。

**Acceptance Scenarios**:

1. **Given** 工作区存在多个 Agent 目录，**When** 启动扫描，**Then** 每个合法
   目录被完整派生并注册，frontmatter 各字段逐项生效。
2. **Given** 其中一个 Agent 目录的文件头非法（缺必填项或格式错误），**When**
   启动扫描，**Then** 该 Agent 被跳过并告警，其它 Agent 不受影响。
3. **Given** Agent 声明了自己的引导文件列表，**When** 组装系统提示词，**Then**
   只有声明的那些文件被注入；未声明时回退到三个默认引导文件并告警。
4. **Given** Agent 目录下的技能目录挂着一个指向公共技能库的软连接，**When**
   组装系统提示词，**Then** 注入内容只有技能名称、描述与本地绝对路径，**不含
   `SKILL.md` 正文**；软连接断链或缺少必需字段时告警跳过，不阻断。
5. **Given** 一轮对话结束后新增了一个技能软连接，**When** 开始下一轮，**Then**
   新技能的元数据已被注入（每轮重扫，不缓存）；移除后下一轮不再出现。

### Edge Cases

- **路径穿越的多种写法**：`../`、`..` 与符号链接等形态经规范化后统一比对；
  越界即拒，不因写法不同而漏放。
- **命令含前导空白**：比对前先去除首尾空白，仍只比对首个 token；大小写逐字
  比对（部署目标为大小写敏感的文件系统）。
- **命令超时**：超时即终止并返回失败，不让进程挂死拖住整轮对话。
- **并发调用同一工具**：两路并发调用的输出不得互相串入（各归各的结果）。
- **白名单为空**：对应类别的动作全部拒绝，不静默放行（部署说明必须写明）。
- **MCP server 启动即失败 / 中途断开**：启动阶段跳过并告警；调用阶段按失败
  结果返回，错误文本回填给模型。
- **MCP 环境变量是明文或占位符未解析**：大声报错拒绝启动，不静默降级。
- **通知渠道未登记 / 渠道名拼错 / 未给渠道名**：一律明确失败并回填可用渠道
  名清单，不猜、不静默当作已送达。
- **通知地址域名不在白名单**：校验先于发送，请求不得发出。
- **技能软连接断链、缺少必需字段、或正文为空**：告警跳过该技能，不阻断
  整轮对话。
- **技能软连接指向公共技能库之外**（越界绑定）：告警跳过、不注入元数据；
  越界绑定不得让模型通过 L1 提示读到公共技能库以外的文件。
- **技能元数据里的路径与文件白名单的关系**：注入的是 Agent 本地路径，位于
  文件白名单之内；解析后的真实目标只用于绑定合法性校验，不进入提示词。
- **引导文件缺失**：告警但继续（引导文件缺失不应让 Agent 完全不可用）。
- **Agent 目录为空或不存在**：视为没有 Agent，启动正常完成。
- **工具名冲突**：先注册者保留，后注册者不覆盖并告警。
- **工具返回失败**：失败结果与错误文本回填进对话上下文，模型可据此调整；
  审计与告警日志两条痕迹都要有。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供九个内置工具：三个文件工具（读文件、写文件、
  列目录）、一个命令工具、两个 HTTP 工具（GET、POST）、两个记忆工具（写入、
  检索）、一个通知工具。
- **FR-002**: 每个文件、命令、HTTP 动作 MUST 在真正发生之前经过对应类别的
  白名单校验。
- **FR-003**: 文件路径 MUST 经规范化后与白名单比对，`../` 等越界写法 MUST
  被拒绝。
- **FR-004**: 命令校验 MUST 只比对命令的首个 token（不做参数级校验）。
- **FR-005**: 任一档白名单配置为空时，该类别动作 MUST 全部拒绝，MUST NOT
  静默放行为"不校验"。
- **FR-006**: 校验失败 MUST 终止该动作并给出明确失败原因；被拒动作 MUST NOT
  真正发生（文件未落盘、命令未启动、请求未发出）。
- **FR-007**: 三类来源的工具（内置、注解组件、MCP）MUST 被统一注册为同一种
  工具，运行时按名取用；模型侧 MUST 只看到工具名、描述与入参 schema。
- **FR-008**: 系统 MUST 支持扫描注册，内置工具与注解组件 MUST 走同一条扫描
  注册路径。
- **FR-009**: 按名查找未命中时 MUST 返回空值，MUST NOT 抛异常给调用方。
- **FR-010**: 每个已注册工具 MUST 提供非空入参 schema（任一工具 schema 为空
  会使全部模型调用失败）。
- **FR-011**: MCP 接入 MUST 采用标准输入输出子进程形态；系统启动时 MUST
  连接配置中的 MCP server 并拉取、注册其工具列表。
- **FR-012**: 单个 MCP server 连接失败或不可用时，系统 MUST 只告警并跳过该
  server，MUST NOT 阻断启动，其它 server 的工具 MUST 正常注册。
- **FR-013**: MCP 工具调用失败时 MUST 以失败结果返回，且错误文本 MUST 回填
  进对话上下文。
- **FR-014**: MCP server 的环境变量 MUST 只允许 `${ENV_VAR}` 占位；明文值
  MUST 被拒绝，占位符解析失败 MUST 大声报错，MUST NOT 静默降级。
- **FR-015**: 通知渠道 MUST 持久化在全局注册表，每项包含名称、类型、地址与
  可选说明；MUST NOT 由 Agent 目录的 frontmatter 承载。
- **FR-016**: 通知工具 MUST 按名解析渠道；渠道名缺失或不存在时 MUST 明确
  失败，并在错误信息中回填可用渠道名清单。
- **FR-017**: 通知发送 MUST 先经过与 HTTP 工具同一份域名白名单校验，且校验
  MUST 发生在发送之前。
- **FR-018**: Agent 目录的文件头 MUST 被完整派生为运行配置，字段包括描述、
  身份、可用工具、引用的 MCP server、引导文件、渠道、定时任务。
- **FR-019**: 系统启动时 MUST 扫描全部 Agent 目录并注册；单个 Agent 配置
  非法时 MUST 只告警、不阻断其它 Agent。
- **FR-020**: 引导文件列表 MUST 按 Agent 的声明生效；声明缺失时 MUST 回退到
  三个默认引导文件并告警；声明指向的文件缺失时 MUST 告警但继续。
- **FR-021**: Agent 绑定的技能，系统 MUST 每轮只注入名称、描述与 **Agent
  本地绝对路径**（即 Agent 目录下 `skills/` 里的软连接路径，非解析后的真实
  目标路径）三项元数据；技能正文 MUST NOT 预载进系统提示词，MUST NOT 进入
  工具注册表。
- **FR-022**: 技能元数据 MUST 每轮重新扫描（不缓存）：新增技能下一轮可见、
  移除后下一轮消失；软连接断链或缺少必需字段时 MUST 告警跳过，不阻断对话。
- **FR-028**（编号非递增：按技术方案 §8.3 补录顺序保留，不重排）: 技能绑定 MUST 校验软连接的真实目标位于公共技能库
  （`.nivroos/skills/`）之内；目标越界的绑定 MUST 告警跳过，MUST NOT 注入、
  MUST NOT 阻断对话（技术方案 §8.3「验证真实目标位于公共 Skill 根」）。
- **FR-023**: 工具执行失败与白名单拒绝 MUST 同时留下审计落库与告警日志两条
  痕迹；异常 MUST NOT 被吞掉（不出现"看起来成功但实际没做"）。
- **FR-024**: 提供给某个 Agent 的工具池 MUST 严格等于该 Agent 声明的工具名
  集合——不多不少；请求调用未声明的工具名时 MUST 告警跳过。
- **FR-025**: 工具名重复注册时 MUST 保留先注册者、不覆盖并告警。
- **FR-026**: 命令工具 MUST 带可配置的执行超时；超时后 MUST 终止命令并返回
  失败，MUST NOT 挂死。
- **FR-027**: 新增 MCP server 客户端依赖 MUST NOT 引入新的第三方坐标
  （依赖已在工具模块声明）；MCP 调用 MUST 走同步模型，MUST NOT 引入响应式
  或自建线程池。

### Key Entities

- **工具（Tool）**：可被模型调用的外部能力，具备名称、描述、入参 schema 与
  执行语义四个要素；三个要素对模型可见，来源对模型不可见。
- **工具注册表（Tool Registry）**：运行期所有工具的登记与查找中心，三类来源
  同一份登记；是上层装配工具池的唯一取用入口。
- **沙箱动作（Sandbox Action）**：一次待执行的动作，含类别（文件读 / 文件写 /
  命令 / HTTP）与目标；白名单校验的对象。
- **通知渠道（Notify Channel）**：出站推送的命名目标，含名称、类型、地址、
  说明；全局共享、持久化、由运维方登记。
- **MCP server 配置（MCP Server Config）**：外部工具进程的接入声明，含名称、
  传输方式、启动命令、环境变量；环境变量只接受占位符。
- **Agent 目录配置（Agent Profile）**：一个 Agent 的运行配置，由目录文件头
  派生；决定它的任务指令、可用工具、引用资源与触发渠道。
- **技能元数据（Skill Metadata）**：技能的名称、描述与本地路径三项；注入
  系统提示词的部分，不含技能正文。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 九个内置工具在真机冒烟中全部被模型成功调用至少一次（通知工具
  以真实群机器人 webhook 收到推送为准）。
- **SC-002**: 越界动作真正发生的次数为 0——路径穿越、白名单外命令、白名单外
  域名、未登记渠道四类各验证一次，全部以"动作未发生"为通过标准。
- **SC-003**: 单个 MCP server 故障场景下启动成功率 100%，其余 server 的工具
  可用率 100%（告警可见）。
- **SC-004**: 已注册工具的入参 schema 非空率 100%；模型调用不因 schema 缺失
  而失败。
- **SC-005**: 工具调用无论成功或失败，100% 可在审计记录中追溯；失败路径 100%
  伴随告警日志。
- **SC-006**: 技能元数据注入内容中技能正文出现次数为 0（人工核对）。
- **SC-007**: 方式一零代码上线一个新 Agent 的代价 = 新增一个目录 + 改一行
  渠道配置，过程中零 Java 代码、零重新构建。
- **SC-008**: 工具池与 Agent 声明的一致率 100%（声明几个就只给几个）。
- **SC-009**: 命令工具超时场景下进程终止率 100%，无挂死。

## Assumptions

- **白名单是劝阻级防线**：应用层白名单防模型犯傻误操作，不防蓄意绕过；核心
  阶段不用它跑完全不可信代码，也不做多租户（技术方案 §6.7 要点一）。
- **脚本可绕过 HTTP 白名单**：命令工具执行 Agent 捆绑脚本时，脚本自身可发起
  网络请求绕过域名白名单——白名单只管内置 HTTP 工具与通知发送；装一个带
  脚本的 Agent 等于信任该 Agent 的作者（技术方案 §12.3 注，须如实告知）。
- **命令只校验首个 token**：命令参数中的路径不做校验（技术方案 §6.7）；要
  加严属行为契约变更，需先裁决。
- **通知只做通用 webhook**：核心阶段用一个通用 webhook 形态覆盖"给一个地址
  发一次 POST 就能送达"的场景；各渠道的 payload 差异与认证细节（签名、
  AccessToken 刷新）留扩展阶段按渠道类型加专用适配器，接口不变。
- **通知渠道由运维方手工登记**：核心阶段不提供增删改查端点与管理台，渠道以
  直接写库方式登记；渠道地址本身即凭证，按凭证纪律处理（占位符注入、不进
  对话、不入库文档）。
- **MCP 只做标准输入输出**：SSE 与 Streamable HTTP 传输、resources / prompts
  消费留扩展阶段；核心阶段只做连接维护、工具列表与工具调用。
- **鉴权上下文不跨边界**：MCP 与通知的域内实现不依赖核心模块的内部类型，
  两者之间的数据形态转换只发生在各自的适配器内部（依赖方向见技术方案
  §10 的模块边界）。
- **同步执行 + 虚拟线程**：工具调用在一轮响应内按顺序执行，不并行；并发能力
  由虚拟线程承载（宪法原则七）。
- **Agent 目录改动需重启**：核心阶段无目录监听与热加载；但 Agent 正文与技能
  元数据按轮重读/重扫，这两类改动下一轮即生效。
- **工具默认参数取值沿用项目既有默认值**：命令超时默认 30 秒；MCP 调用超时
  默认 30 秒；HTTP 工具沿用既有 10 秒超时；POST 默认以 JSON 形式发送请求体；
  通知请求体为通用的 `{"content": "<文本>"}` 形态；工具重名不覆盖、保留先
  注册者。以上均为颗粒度文档「待决事项」登记的默认建议值，实施期间如需变更
  属软门禁，停下报告。
- **技能元数据的必需字段是名称与描述**：两者缺一即视为无效技能，告警跳过；
  技能正文为空不算无效（正文不参与注入判定）。
- **MCP 工具未声明入参 schema 时由适配层补空对象 schema**：为保证"每个工具
  入参 schema 非空"的契约成立，缺失时以空对象 schema 兜底，而不是让一个
  外部 server 的疏漏拖垮全部模型调用。
- **未登记或类型不受支持的通知渠道明确失败**：核心阶段只有通用 webhook 一档
  适配器，登记为其它类型时按"渠道不可用"处理，错误信息回填可用渠道名清单。
- **无新增第三方依赖**：MCP 客户端坐标已在工具模块声明；其余实现使用运行时
  与既有依赖（技术方案 §6.4）。
- **内网部署假设**：核心阶段不做认证与限流，假定部署在企业内网（需求文档
  §5.10 与项目既定边界一致）。

## Dependencies

- **依赖 US-1 交付**：模型供应商抽象、调用审计能力与配置加载基础版（本模块
  的 MCP 环境变量解析沿用同一套占位符纪律，但不复用命令行侧实现，避免反向
  依赖）。
- **依赖 US-2 交付**：ReAct 循环、工具执行器、会话管理、上下文组装器、
  工具池装配（命令行入口）、沙箱接口与 HTTP 档白名单、HTTP GET 工具。本模块
  需要扩展沙箱实现类构造签名、给既有工具换注册机制与注解标注、改造命令行
  装配——这三处已在颗粒度文档 §3.2 列为前序改造点，实施时停下报告。
- **依赖 US-3 交付**：两个记忆工具（本模块只换注册机制与标注方式，工具名与
  参数名保持不变）。
- **外部依赖（人工项）**：真实社区 MCP server（方式一/方式二真机冒烟）、
  真实群机器人 webhook（通知真机冒烟）；核心阶段的自动化测试不触碰真实网络。

## Out of Scope

- 让模型框架自动执行工具（框架只做 schema 生成与协议翻译）
- 工具调用并行（一次响应内的多个调用按顺序执行）
- MCP 的 SSE / Streamable HTTP 传输（只做标准输入输出）
- MCP 的 resources / prompts 消费（只做工具列表与工具调用）
- 容器 / microVM 沙箱、脚本的网络隔离
- Agent 级工具策略（allow / deny）
- 企业微信 / 飞书 / 钉钉专用 API（签名算法、AccessToken 刷新）
- 通知渠道的增删改查端点与管理台
- Agent 目录热加载 / 实时监听（改配置需重启）
- 技能正文预载（只注入元数据，正文按需读取）
- 命令参数中的路径校验（只校验首个 token）
- 命令的资源占用限制（CPU / 内存限额，随容器沙箱一并留扩展阶段）
